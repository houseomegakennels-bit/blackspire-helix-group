# Owned PostgreSQL bootstrap

This component prepares a separate PostgreSQL 17.6 cluster. It does not copy production data, create authentication tables, publish credentials, activate a release, or claim production readiness. Existing writer SQL/catalog checks remain unchanged. The descriptor binds the fixed endpoint, observed creator OID, observed cluster system identifier and certificate authority digest; a hostname alone is not cluster identity.

`bash scripts/with-node.sh scripts/prepare-zola-owned-postgres.mjs /absolute/new/directory` writes an exclusive preparation packet with synchronized files and content hashes. It runs no SQL or Docker commands. A failed partial packet is retained for inspection; it is never overwritten on retry.

The executable root command is `bash scripts/with-node.sh scripts/materialize-zola-owned-postgres.mjs --release-sha <exact-reviewed-release-sha>`. It requires the clean literal release branch and matching fixed remote head, existing valid global release journals, stopped API/worker/gateway services, root-owned canonical parent directories, cached image and at least 8GiB free on the separate build volume. It creates only the isolated empty database infrastructure; it does not migrate or activate application data.

The helper retains a protected state and per-stage intents/results under `/var/lib/blackspire-operator/owned-postgres-materialization`. Existing foreign network/volume/container/configuration names refuse. An intent with an incomplete observed effect is never replayed automatically; retain and inspect that prefix. Fully observed outcomes may complete their missing result without repeating the effect. Completed historical bootstrap stages are not rerun; final acceptance revalidates current container/network/TLS/profile and reads the actual database boundary over TLS.

The host materializer performs this sequence under its durable intent and exclusive deployment guard:

1. Verify the exact reviewed source, stopped application services, source database quiescence and absent target state. Verify the cached pinned image and its PostgreSQL UID/GID 70:70. Do not pull an image into the nearly full root filesystem.
2. Create and inspect a dedicated Docker network named `blackspire-owned-postgres` with `Internal=true`, no other attached containers and no provider route. The container publishes no Docker host port: actual internal-network testing found Docker leaves that binding null. A root-owned systemd socket-proxyd listens on 127.0.0.1:55432 and forwards TLS bytes to the exact retained internal container IP. Network/container IDs and IP must still match; drift refuses. The proxy has bounded connections and service resources, plus IP allowlists for loopback and that one target. A same-name foreign network or container must refuse rather than be adopted.
3. Prepare `/mnt/blackspire-builds/zola-owned-postgres/data` on the mounted build volume, owned 70:70 and mode0700, with sufficient measured data/WAL/backup reserve. Retain configuration and TLS material under `/etc/blackspire/owned-postgres/server`; directories must permit PostgreSQL traversal while the private key is 70:70 mode0600. Server certificate must verify against the protected CA and contain IP SAN 127.0.0.1. No provider credential is mounted into the container.
4. Initialize only the empty data directory using the fixed image, `--network none`, user70:70, and `initdb -D /var/lib/postgresql/data -U blackspire_cluster_admin --auth-local=peer --auth-host=scram-sha-256`. Never use POSTGRES_HOST_AUTH_METHOD=trust for a persistent cluster. The bootstrap superuser is OID10, has no password and is accessible only through local peer mapping from the container PostgreSQL OS user. The final HBA grants it no TCP route.
5. Materialize the packet's PostgreSQL configuration and create the exact pinned container. Inspect all mounts, image, user, internal network, absence of Docker port publication, capabilities, memory/CPU/PID/log limits before starting. The systemd unit assumes this exact validated container already exists; it does not recreate or adopt one.
6. Through `docker exec --user 70:70` and local peer authentication, run template1.sql against template1 and bootstrap.sql against postgres with psql -X and ON_ERROR_STOP. The database bootstrap is one transaction and refuses an existing postgres role or nonempty application namespace. A crash between template and database transactions requires observation of the retained prefix, never blind rerun. Observe owner, role flags, cluster identifier, template1 and complete catalog before considering bootstrap complete.
7. Record the exact observed descriptor in root0600 profile.json. The postgres management role initially has NOLOGIN and no password. The materializer durably retains its new credential before enabling LOGIN through stdin-only SQL; it binds that credential to the profile digest and verifies an actual authenticated TLS connection before reporting success. Runtime/repository roles are not created by bootstrap. Their dedicated provisioning and schema migrations are separate reviewed steps.
8. Apply the reviewed canonical schema/data migration and repository grants, then the unchanged writer installer and full owned-cluster boundary verifier. Refuse pg_net, FDW, dblink, foreign servers/mappings and PUBLIC-derived writer access. Only a complete reconciled migration with all readers routed to the sole canonical destination can activate the release.

Rollback before cutover stops the owned service and preserves its data and preparation evidence. After any canonical writes, returning to the old source requires a separately verified reverse-copy plan; changing the endpoint alone would lose new state. This packet has no automatic destructive cleanup or rollback.

Resource defaults are 768MiB memory, one CPU, 128 PIDs, 128MiB shared buffers and bounded container logs (3x10MiB). Data and WAL share the build-volume directory. `max_wal_size` is a checkpoint target, not a hard storage ceiling; monitoring, storage reserve and backup retention remain deployment requirements.

`test-zola-owned-postgres.mjs` uses a network-disabled disposable container with no host data mounts. Its canonical-shaped schema verifies unchanged installer compatibility and unsafe PUBLIC sequence rejection; fixture authentication is not evidence of production schema/auth migration. Production TLS, systemd, volume durability and end-to-end migration remain unverified until their host acceptance runs.

`test-zola-owned-transport.py` independently proves the actual internal Docker network, loopback socket activation, systemd-socket-proxyd and CA-verified PostgreSQL TLS/SQL path with an IP SAN. The shared owned TLS helper explicitly verifies 127.0.0.1 because pg omits SNI for IP hosts; verification is never disabled. The production systemd unit installation itself remains unexecuted until review.
