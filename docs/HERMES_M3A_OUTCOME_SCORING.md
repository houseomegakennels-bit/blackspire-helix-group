# Hermes Milestone 3A — Verified Outcome Scoring and Immutable Provenance

Phase 3A records append-only, redacted factual evaluations of newly completed Hermes workflow runs. It does not promote memory, retrieve memory, create scorecards, alter routing, backfill history, or run a live provider.

An internal evaluator runs only after a terminal workflow has ordered Hermes steps. It stores one row per `(run_id, evaluation_version)` and records a SHA-256 digest over the complete canonical packet: normalized task identity, evaluation identity and creation time, every ordered workflow step, every routing/policy/verification decision, every provider attempt, and every persisted component. The evaluator proves canonical task/workspace/conversation/actor/channel/objective scope, terminal status/outcome agreement (including factual no-dispatch execution refusal), exact stage-bounded step and subordinate-row chronology, exact received/normalized/policy/route/execution/verification agreement, run agent/provider/cost agreement, enabled selected routing, policy/approval agreement, the exact deterministic verifier check set, provider status/timeout/cancellation agreement, valid retry history, complete verified-run evidence, bounded integer usage, exact redaction, and deterministic ordering before inserting anything. Duplicate creation, incomplete, contradictory, or malformed evidence, hidden subordinate rows, scope drift, redaction-equivalent secret injection, unordered steps, and nonterminal runs fail closed.

`m3a-v1` components are transparent: completion, deterministic verification, confidence class, retry count, duration, timeout, cancellation, known provider cost, and explicit unknown user-acceptance, rollback, and stability signals. Silence is never stability. Only a completed verified run is `positive_eligible`; blocked runs are `ineligible_blocked`; other terminal outcomes are factual negative evidence. These labels do not affect routing.

The project boundary is currently identical to the workspace boundary because the canonical task model has no separate project identifier. Cross-workspace evaluation access is not introduced.

## Authorization and read surface

PR #58's merged canonical authorization foundation is the only authority for Phase 3A evaluation reads. A request cannot select a principal, role, permission, workspace, or authentication method. The read endpoint accepts a single evaluation ID, derives its workspace from the stored record, resolves the server-configured canonical **admin bearer** principal, and requires that principal's current active `evaluation.read` grant. A cookie session can reach this read only when server-side login has bound it to that same configured canonical admin principal; an unbound, stale, revoked, disabled, expired, forged, service, or differently bound session fails closed. Bearer behavior is unchanged. Missing, guessed, malformed, and cross-workspace IDs share the same unavailable result. The PWA's optional `?evaluation=<id>` view renders only that sanitized summary, and its script/style are external so the production CSP remains strict.

The response intentionally omits prompt text, classification JSON, provider payloads, components, credential references, hidden reasoning, and raw evidence. Authorization decisions are audited by the canonical service; an audit-write failure fails closed. There is no unscoped evaluation listing endpoint.

## Additive correction and evidence policy

Evaluations and their components are protected by database update/delete refusal triggers in addition to the absence of mutation helpers. Corrections are append-only records tied to one existing evaluation and therefore its immutable workflow and workspace. Each correction has a required reason and explicit source evidence; it must supersede the sole current correction head. The unique parent link plus transactional service checks reject duplicate versions, branching, cycles, absent parents, concurrent authority loss, actor/grant issuance after the claimed evidence time, and cross-run or cross-workspace links. `evaluation.correct` is audited durably before the mutation transaction, then current authority is revalidated without another decision write immediately before insertion inside that transaction. A denial therefore retains its audit, while authority lost after an allowed decision still prevents insertion. Read-only history exposes correction metadata but never the actor identifier or raw evidence, and validating a historical actor uses the pure current-authority check rather than fabricating a new correction decision. Phase 3A uses a **current-authority** read model: subordinate evidence remains readable only while its persisted canonical admin/service actor is active, lifecycle-valid, has a valid workspace grant, and currently retains `evaluation.correct`; revocation, expiry, disablement, grant loss, permission loss, or evidence predating the actor/grant fails the related evaluation read closed. It does not infer or preserve an event-time human identity snapshot.

Source evidence is also database-enforced append-only. Allowed event types are `accepted`, `rejected`, `partially_accepted`, `rollback`, `follow_up_verification`, `stability_confirmed`, and `regression_linked`. Every event requires a trusted currently authorized actor, an intact existing evaluation, explicit evidence, and a bounded unique idempotency key; its permission is likewise audited durably before the mutation transaction and revalidated without a second audit immediately before insertion, so replay, duplicate keys, and concurrent authority loss fail. Silence remains unknown. These events do not change routing, scorecards, task execution, or memory.

## Failure observability and operations

The terminal evaluator records a sanitized `open` evaluation-failure record when it cannot create an evaluation. It contains only the run/workspace linkage, bounded category, remediation state, and generic detail—never the caught error payload. It creates no retry loop. A future operator-owned retry must be explicit, bounded, and idempotent.

Migrations are additive, idempotent, and publish schema changes atomically. Named uniqueness indexes and immutability triggers are required schema objects, so startup/restore validation fails closed when integrity-critical structure is missing. Rollback is code rollback: existing Phase 3A tables remain inert immutable evidence and must not be edited or deleted. Development/test fixtures use disposable SQLite databases only. The authorization provisioning CLI is development/test-only, refuses production and shared paths, validates the complete grant graph and lifecycle contract, and never auto-runs at startup.

## Status and limitations

Phase 3A uses the merged authorization foundation, but it does **not** protect any other HTTP route, create verified human identities, provision real principals or grants, run a live provider, perform historical backfill, update scorecards, alter routing, or promote/retrieve memory. Phase 3B verified scorecards and learning-quality evidence are deferred; learned routing remains later still. PR #57 is in final stabilization/validation and is not merged until exact-head CI, Vercel, thread, and independent-review gates pass. Production is disabled and Gate 4 remains unauthorized.
