# Blackspire Decisions

## 2026-08-04 — A local backup is observable evidence, not disaster recovery

The latest-backup verifier proves local recency, checksum binding, SQLite integrity, and current schema compatibility read-only. It deliberately cannot repair, rotate, upload, restore, or delete. A green local snapshot does not survive host loss and cannot establish RPO/RTO, encryption/key custody, off-host separation, retention, or recovery time. Those remain operator-owned requirements and must not be defaulted by code.

## 2026-08-04 — `chain_version` is the sole ordering authority; `created_at` is metadata

A re-review chain orders strictly by `chain_version`, and `created_at` carries no ordering guarantee. Wall-clock time is not a safe ordering key for an append-only chain: it is not monotonic across restarts or hosts, and nothing prevents two rows from sharing a timestamp. `UNIQUE(root_review_id,chain_version)` makes the ordering both total and enforceable by the database rather than by convention, so a gap or a fork cannot hide off the walked path. `created_at` is therefore stored as metadata, hashed into neither the content nor the lineage packet, and no re-review query orders by it. The read path deliberately does **not** verify `created_at` monotonicity, and that is recorded as a known non-guarantee rather than left implicit.

## 2026-08-04 — A guard pair that is individually redundant may still be jointly load-bearing

Milestone 3C's second slice contains two guards — the write-path whole-chain validity check and the predecessor-intactness call — where deleting **either alone** leaves the entire suite green, but deleting **both together** fails three tests. One-mutant-at-a-time mutation testing is structurally blind to this: it can only ever report each as an equivalent mutant, which reads as "this guard is dispensable" when the truth is "these two are redundant with each other and jointly indispensable". The standing rule taken from this: a declared-equivalent mutant whose justification appeals to another guard's behaviour must say so explicitly and must be marked conditional on that guard, and a green mutation run must never be read as proving any single guard removable. The harness's own rationale now discloses this in the committed inventory rather than presenting a clean equivalence. "0 surviving" is a statement about the **committed mutant inventory**, never about the module.

## 2026-08-04 — An unverified rationale in evidence text is a defect, not a typo

Four evidence defects entered the record across PR #64, and independent review rather than self-check caught every one. Three were claims asserted without verification: a harness exit-code behaviour that execution refuted, a concurrency window that reading the parent commit refuted, and a declared-equivalent rationale naming an identifier (`INHERITED_VALUE_KEYS`) that exists nowhere in the repository. The fourth was the mirror image — not a false claim but a silent omission, a guard whose mutant was missing from the committed inventory while the status document asserted it was there. The first two were retracted in place, the third corrected, the fourth added. The rationale text attached to a declared-equivalent mutant is precisely what an auditor relies on to accept that mutant as equivalent rather than surviving, so a wrong symbol or an unverified justification in it is an **evidence defect** of the same class as a wrong test result — it is load-bearing, not commentary. The standing rule: retract in place with the retraction visible in the record rather than quietly editing, and never assert a mechanism in evidence text without executing or reading the thing that would refute it.

## 2026-08-04 — Milestone 3C's second slice merged; the review queue is next, promotion is not

PR #64 merged as `0d6e977113e826095c4ed57db150bf30d9de954f` from exact reviewed head `055cd5bd919b2ddc2f94113e07134bb8b72829cc` only after two independent exact-head reviewers both returned unconditional `approve` on that exact SHA, under an expected-head merge guard. Re-review and successor chains authorize nothing: the write path has no production caller, the only surface is GET-only, and appending never mutates candidate `status` or `promoted_at`. The workspace-scoped review queue comes next, and only then promotion. Promotion must not inherit `evaluation.correct` as its authority without an explicit decision, and must never be automatic.

## 2026-07-31 — A review is a new append-only row, never a candidate status update

Milestone 3C records a human judgement about a memory candidate as a row in the new `hermes_memory_candidate_reviews` table, and deliberately not as a `status` update on `hermes_memory_candidates`. That Milestone 1 table has no immutability triggers, and its `status` and `promoted_at` columns *are* the promotion mechanism: introducing the first UPDATE path against exactly those columns would make "review-only" a code convention that any later edit could quietly revoke. Keeping the write in a separate append-only table makes the boundary structural — enforceable by a database CHECK with no `promote` value and by the absence of any writer at all — rather than a property of reviewer vigilance. Because the candidate table stays mutable, a review pins `candidate_digest` over an explicit column list, which is the only thing that turns "reviewed candidate X" into "reviewed candidate X as it then was". The explicit column list, rather than a whole-row hash, means a column added by a later migration cannot silently invalidate every stored review.

## 2026-07-31 — A refusal must not disclose what the caller was not authorized to see

Milestone 3C's record path originally resolved and validated the candidate row before authorizing, so an absent candidate and a real candidate in another workspace refused with different messages. That is an existence oracle: one workspace grant plus well-formed ids enumerates the memory candidates of every other workspace. The standing rule taken from this: on any path where scope is derived from the stored object, absence, an unusable scope, and a denied scope must refuse **identically**, and only a caller already authorized in the object's own scope may receive differentiated diagnostics. The read path already worked this way; the record path must not be the weaker of the two. A residual asymmetry is accepted and documented rather than hidden — a denial is audited against the object's workspace while absence names no workspace to audit against — because auditing denials is worth more than closing a channel visible only to a reader of the audit log. Any future recording surface must satisfy this rule before it is exposed over HTTP.

## 2026-07-30 — Phase 3A evidence is complete, immutable, and non-operative

An outcome evaluation is trustworthy only when its digest binds the evaluation ID/time, persisted components, and every ordered workflow, routing, policy, verification, and provider-attempt row after canonical scope, timestamp, domain, retry, usage, provider, and exact-redaction validation. Evaluations, components, corrections, source events, and failure records are database-enforced append-only; corrections and source events combine current authorization and insertion in one transaction. These records remain factual inputs only. Verified scorecards are a separate Phase 3B milestone; approval-gated memory promotion and learned routing remain later and cannot be inferred from `positive_eligible`.

## 2026-07-27 (later)

- PR #41 (`fix/restore-reject-empty-invalid-backup`) is merged into `origin/main` as `d800d283b11b03d88c519e18abbed0870d9fa750` (reviewed head `40e6d6a873e1579b91004736ba55e2ab87f2e462`), which becomes the verified implementation anchor.
- A backup or restore is never trusted on the strength of `PRAGMA integrity_check` alone. SQLite treats an empty or zero-byte file as a valid, newly-created database with zero tables, so integrity alone cannot prove a file is a real Blackspire database. This was reproduced directly against the pre-fix `scripts/restore.js`, which printed `{"ok":true}` and exited `0` for a 0-byte backup carrying a matching checksum sidecar.
- Restore proves schema completeness independently of integrity: it refuses a zero-byte backup before opening it, validates the backup against the required Blackspire schema before copying, re-validates the copy rather than trusting that the copy succeeded, and publishes atomically through a uniquely named temp file plus a link that refuses `EEXIST` instead of silently replacing a destination.
